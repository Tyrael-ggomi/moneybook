# Dropbox 자동 백업 설계 메모

상태: 설계/구현 준비 단계 (아직 자동 백업 기능이 배포된 상태가 아님)

## 목표 동작

- 머니북의 실제 데이터가 Supabase PostgreSQL에 성공적으로 저장된 시점을 기준으로 대기 시간을 계산한다.
- 마지막 데이터 변경 후 **10분 동안 추가 변경이 없으면** 백업을 한 번 실행한다.
- 카드/카테고리/자동분류/이름 설정, 지출 추가·수정·삭제·일괄 작업, 메모 등 복구 대상 데이터의 변경을 모두 포함한다.
- 백업 파일은 암호화한 뒤 Dropbox의 머니북 전용 앱 폴더에 업로드한다.
- 성공/실패, 실행 시각, 파일명, 파일 크기, 오류 요약을 머니북에서 확인할 수 있게 기록한다.
- 실패한 백업은 다음 서버 기동/접속 시 다시 확인하고 재시도한다. 최신 변경이 반영되지 않은 백업을 성공으로 표시하지 않는다.

## Render 무료 플랜 고려사항

Render 무료 웹 서비스는 일정 시간 외부 요청이 없으면 잠들 수 있다. 서버 안의 대기 타이머만 믿지 말고, 마지막 변경 시각과 백업 상태를 Supabase에 영속적으로 기록해야 한다. 서버가 다시 깨어나면 만료된 예약을 재검사한다. 10분 타이머는 마지막 변경 후 10분 시점에 실행을 시도하는 것이며, 서버 기동/외부 서비스 지연 때문에 완료 시각을 절대 보장하지는 않는다.

## 구현 원칙

1. 백업 대상은 Supabase 프로젝트 설정 전체가 아니라 머니북의 데이터베이스 테이블/데이터다.
2. 임시 파일을 Render 디스크에 영구 보관하지 않는다. 생성한 파일은 업로드 후 임시 파일을 정리한다.
3. Dropbox 자격 증명과 암호화 키는 GitHub 소스 코드나 DB에 넣지 않는다. Render 환경 변수로만 보관한다.
4. 암호화 키는 별도 안전한 장소에 보관해야 한다. 키를 잃으면 백업을 복호화할 수 없다.
5. Dropbox 업로드 실패나 잘못된 인증은 민감한 토큰을 로그/화면에 노출하지 않고, 일반화한 오류를 기록한다.
6. 백업 파일은 버전 정보, 생성 시각, 테이블/컬럼 정보 및 행 데이터를 포함한 복구 가능한 형식으로 만든다. 단순 CSV 묶음이 아니라 데이터 타입과 관계를 고려한다.
7. 첫 적용은 기능 브랜치에서 검토하고, 설정 누락 시 앱의 일반 사용/기존 저장 동작을 방해하지 않게 한다.

## 필요한 Render 환경 변수 (실제 값은 소스 코드/채팅에 기록하지 않음)

- `DROPBOX_APP_KEY`
- `DROPBOX_APP_SECRET`
- `DROPBOX_REFRESH_TOKEN`
- `DROPBOX_BACKUP_PATH` (예: `/apps/moneybook-backup`)
- `BACKUP_ENCRYPTION_KEY`

Dropbox는 앱 폴더 접근만 허용하도록 설정한다. 토큰은 권한 범위를 최소화한다.

## 구현 전 검증 항목

- 성공적으로 저장된 변경이 10분 동안 추가 변경 없이 유지된 경우에만 백업 예약이 만료되는가?
- 예약 만료 전 새 변경이 생기면 만료 시각이 새로 계산되는가?
- 여러 탭/요청이 겹쳐도 같은 시점에 중복 업로드하지 않는가?
- 업로드 실패가 성공으로 표시되지 않고 재시도 가능한가?
- JSON/압축/암호화 파일이 실제로 Dropbox에 생성되는가?
- 백업 안에 지출 데이터, 카드/카테고리/설정/메모가 포함되는가?
- 비밀 정보가 화면/서버 로그/저장소에 노출되지 않는가?
- 기존 머니북 로그인 및 CRUD 동작에 회귀가 없는가?

## 사용자 확인이 필요한 작업

Dropbox 앱 콘솔에서 앱을 만들고, App folder + 필요한 OAuth 권한으로 설정한 다음 refresh token을 발급해야 한다. 비밀 값은 사용자 본인만 Render 환경 변수에 입력하며, 채팅에 붙여 넣지 않는다.
